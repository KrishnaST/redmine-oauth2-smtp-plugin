Redmine Microsoft 365 SMTP OAuth2

Install and configure direct Microsoft 365 email delivery for native Redmine notifications. No external automation service, SMTP proxy or incoming-mail ticket creation.

Prepared 22 October 2026. Steps below are instructions, not a record of completed production installation.

1. Scope and prerequisites

The plugin replaces the outgoing transport when enabled. Redmine continues to decide which users receive notifications, based on its existing permissions and preferences.

Outbound only. This plugin never reads a mailbox or creates tickets. It does not disable existing incoming-mail integrations; manage those separately.

Other Redmine versions require separate validation.

  • Allow outbound HTTPS 443 to login.microsoftonline.com.
  • Allow outbound SMTP 587 to smtp.office365.com.
  • No new inbound firewall port, database table or production gem is required.

Initial release: one global sending mailbox, commercial Microsoft cloud, client-secret application authentication. No delegated sign-in, Graph transport or certificate-assertion support.

2. Microsoft 365 setup

2.1 Register an Entra application

  1. Create a dedicated, single-tenant application for Redmine in Microsoft Entra.
  2. Record its Directory (tenant) ID and Application (client) ID.
  3. Add the Office 365 Exchange Online application permission SMTP.SendAsApp; obtain tenant administrator consent.
  4. Create a client secret. Securely retain its value, not just its secret ID, and record its expiry.

This plugin uses client_credentials and the scope https://outlook.office365.com/.default. It does not need browser redirects, a refresh token or Microsoft Graph Mail.Send.

2.2 Authorize the sending mailbox in Exchange

Have the Exchange administrator register the application's service principal and grant the required mailbox access and Send As rights only for the intended sender. The Enterprise Application Object ID differs from the App Registration Object ID; use Microsoft's procedure to select the correct IDs.

Follow the Microsoft application-authentication procedure. Verify the resulting scope before enabling the plugin.

2.3 Check SMTP AUTH policy

The administrator must confirm that tenant and mailbox policies permit the required SMTP AUTH access. Read-only Exchange Online checks:

# Run after connecting to Exchange Online with your approved admin process.
Get-TransportConfig | Format-List SmtpClientAuthenticationDisabled
Get-CASMailbox -Identity redmine@example.com |
    Format-List SmtpClientAuthenticationDisabled

A mailbox setting of False enables it; True disables it; an unset value inherits the tenant setting. If approved, the administrator can enable SMTP AUTH for that mailbox:

Set-CASMailbox -Identity redmine@example.com -SmtpClientAuthenticationDisabled $false
Policy review required. Microsoft documents that Security Defaults can block SMTP AUTH. A mailbox toggle is not proof of access. Do not disable organization-wide protections or enable Basic authentication as a workaround. Have the security administrator approve an appropriate policy or choose another sending design. See Microsoft SMTP AUTH policy guidance.

3. Build and install the plugin

3.1 Build the installation archive on Windows

Set-Location '/path/to/redmine-oauth2-smtp-plugin'
.\tools\package.ps1

Output: dist\redmine_microsoft365_smtp-1.0.0.zip. The ZIP contains the required top-level folder redmine_microsoft365_smtp, regardless of the repository's name. Git metadata and build outputs are excluded.

3.2 Transfer and extract

Transfer the ZIP to the Redmine server using your approved SSH/SFTP process. Inspect its entries before extraction:

unzip -l /path/to/redmine_microsoft365_smtp-1.0.0.zip
cd /opt/redmine
test ! -e plugins/redmine_microsoft365_smtp && echo 'Install directory is available'

If the directory already exists, stop: review the existing version and prepare an upgrade/rollback plan rather than overwriting it. For a new installation, extract as the Redmine service user:

cd /opt/redmine
unzip /path/to/redmine_microsoft365_smtp-1.0.0.zip -d plugins
test -f plugins/redmine_microsoft365_smtp/init.rb

The final path must be /opt/redmine/plugins/redmine_microsoft365_smtp/init.rb. Do not install it under the repository name redmine-oauth2-smtp-plugin.

No plugin database migration or bundle update is required. Do not upgrade the host's gems as part of these steps. Preserve the existing SMTP configuration for rollback.

3.3 Run isolated tests

cd /opt/redmine
bundle exec ruby plugins/redmine_microsoft365_smtp/test/run.rb

Use the same Ruby and bundle as the service. Tests use simulated HTTPS and loopback SMTP, fictitious credentials and temporary files. They do not send real email or access the database.

4. Configure the application credential

Credentials are deliberately not entered into the plugin settings form or stored in the Redmine database. Use a restricted file, or an approved service environment variable.

4.1 Provision a private secret file

Create a protected directory, then use your approved secret-provisioning process to write the client-secret value to /etc/redmine/secrets/m365-client-secret. The file must contain only the value, with an optional trailing newline.

sudo install -d -o redmine -g redmine -m 0700 /etc/redmine/secrets
# Provision the secret securely here. Do not put its value in shell arguments.
sudo chown redmine:redmine /etc/redmine/secrets/m365-client-secret
sudo chmod 0600 /etc/redmine/secrets/m365-client-secret
sudo -u redmine test -r /etc/redmine/secrets/m365-client-secret
stat -c '%a %U %G' /etc/redmine/secrets/m365-client-secret

The plugin rejects symlinks, non-regular files, files over 4096 bytes, unsafe ownership and any group/other permissions. Protect the parent directory too. Account for SELinux using your host's approved file-label policy; do not disable SELinux.

4.2 Expose its path to the service

Use a systemd drop-in:

sudo systemctl edit redmine.service

Enter the following nonsecret setting:

[Service]
Environment="REDMINE_M365_CLIENT_SECRET_FILE=/etc/redmine/secrets/m365-client-secret"

Apply the same variable to every background-worker service that delivers Redmine mail. If using an existing environment file instead, preserve its format, ownership and access permissions.

VariableBehavior
REDMINE_M365_CLIENT_SECRET_FILEPreferred. Absolute path to the protected secret file.
REDMINE_M365_CLIENT_SECRETAlternative secret value supplied by the service environment. Do not disclose it through diagnostics, screenshots, source control or commands.

The file variable takes precedence. An unreadable or unsafe file causes failure; it does not fall back to the alternative value.

4.3 Restart after installation and environment changes

sudo systemctl daemon-reload
sudo systemctl restart redmine.service
systemctl is-active redmine.service

Restart affected mail-worker services through your normal operating procedure as well. The plugin is still disabled until enabled in its settings.

Sign in as an administrator and open Administration → Plugins → Microsoft 365 SMTP OAuth2 → Configure.

Settings path: /settings/plugin/redmine_microsoft365_smtp, with any configured Redmine URL prefix.

The SMTP server, port, TLS requirement and OAuth flow are fixed in the plugin. Do not paste an access token into Redmine's native SMTP password field.

Set Redmine's normal emission email address to the intended mailbox for consistency. Review notification events, user preferences and background-job configuration separately. The plugin sets From and the SMTP envelope sender to its configured mailbox; Reply-To is retained.

Enabled delivery fails closed if settings, tokens or SMTP authentication are invalid. There is no fallback to the old Basic-auth SMTP transport. Redmine's generic settings page saves values without testing them; validate before broad use.

6. Test and enable

  1. Confirm prerequisites and save the plugin with its enable checkbox selected during the approved test window.
  2. Use the settings-page link to open /admin/microsoft365_smtp/test.
  3. Click Send one test email to me. This sends a static message only to the signed-in administrator's own primary email address. Sudo-mode reauthentication may be required.
  4. Check the inbox and Microsoft message trace. SMTP acceptance does not prove inbox delivery.
  5. Perform an authorized ordinary issue-notification test. Check expected recipients, Bcc privacy, attachments and queued delivery.
  6. Check failures and queue status before allowing routine traffic. Disable the plugin and investigate if any required check fails.

Never test using arbitrary client recipients or confidential ticket content. Incoming-mail ticket creation is outside this plugin and should remain disabled if not wanted.

7. Operations and credential rotation

  • Tokens are cached in process memory and renewed before expiry. A mutex coordinates renewal across threads; workers have separate caches.
  • Monitor ordinary Redmine delivery failures and job queues. Coordinate worker concurrency with Microsoft mailbox limits.
  • Keep notification permissions and recipient policies in Redmine. This plugin does not grant users additional ticket access.
  • Do not enable SMTP wire/MIME debug logging in production; it may reveal credentials, recipients or message content outside this plugin's safe errors.

Rotate the client secret

  1. Create a replacement credential in the same dedicated Entra application before the old credential expires.
  2. Update the protected file through the approved secret process, preserving its ownership and permissions. Prefer an atomic replacement to avoid partial reads.
  3. File-content changes are detected on the next token request and invalidate the old cache key. Environment-value changes require restarting all affected processes.
  4. Explicitly verify a test delivery, then retire the previous credential after the agreed overlap period.

The plugin does not automatically resend after an uncertain SMTP submission, since doing so may create duplicate notifications. Review your job system's retry policy separately.

9. Rollback

  1. Uncheck Enable Microsoft 365 SMTP and save. New deliveries then use Redmine's original configured transport.
  2. If that old transport was already failing, disabling the plugin does not repair it. Reconcile failed or uncertain notifications before replaying jobs.
  3. If removing the plugin, move its exact directory out of plugins through the approved change process and restart web/worker services. No migration rollback is needed.
  4. Remove only this plugin's environment/drop-in configuration if no longer used; do not remove unrelated service settings.
  5. Revoke the dedicated Microsoft credential and mailbox permissions when the integration is permanently retired.
